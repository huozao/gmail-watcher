# 海尔验证码自动流转与跨网络传递方案设计

> **文档状态**：历史候选方案。现行链路与验收见 [邮件中枢交接](https://github.com/huozao/mail-hub/blob/main/docs/handoff.md)。
> **涉及系统**：`gmail-watcher` (GCP Cloud Run)、`webdock2` (内网自动化运行环境)、`txecs` (公网中心节点)  
> **涉及业务**：海尔系统账号中心（`iam@haier.com via 163.com`）登录验证码流转  

---

## 1. 背景与目标

### 1.1 业务场景
用户使用特定 Gmail 邮箱接收系统验证码邮件，近期典型邮件特征如下：
- **发件人**：系统账号中心 `iam@haier.com via 163.com`
- **收件人**：`<转发账户>`（转发至 Gmail）
- **内容示例**：`您的验证码为: <六位验证码> (15分钟内有效)`

### 1.2 核心诉求
1. **人工感知端（“发给我”）**：当识别到邮箱变动且为特定发件人（`iam@haier.com`）时，提取邮件关键内容，实时发送给用户（如飞书/企微/邮件），便于人工即时查阅与留底。
2. **程序消费端（“给 Webdock2 登录”）**：登录程序部署在私有内网节点 `webdock2` 上。在触发登录后，程序需要能够自动获取对应的验证码，填入登录页面完成身份认证。

---

## 2. 现实约束与设计考量

在设计传递机制时，必须面对以下物理与架构约束：

1. **网络拓扑不对称（NAT 边界）**：
   - `gmail-watcher` 运行于海外 Google Cloud Run，属于公网 Serverless 容器，出口 IP 动态且实例随时可能缩容至 0。
   - `webdock2` 部署在家庭/办公室局域网（Windows 11 WSL2），没有公网 IP 和开放端口。
   - **约束结论**：公网 Cloud Run 无法主动直连内网的 Webdock2；但 Webdock2 主动发起公网出站（Outbound HTTP）天然畅通无阻。
2. **时序与生命周期敏感**：
   - 验证码有效期一般为 15 分钟，而自动化登录脚本等待验证码的超时窗口通常在 30 ~ 60 秒。
   - 必须防范**脏读历史旧码**（必须只消费当前登录动作触发的新码）以及**重复消费**（一次性原则）。
3. **架构解耦与高可用**：
   - 邮件抵达与登录程序的运行在时间上可能是异步的（可能先触发登录再等邮件，也可能是邮件到达后唤起后续流程）。
   - 中间必须存在可靠的“状态暂存与缓冲介质”，不能依赖容器内存（易因实例缩容丢失）。

基于上述考量，我们设计了 **方案 1（自包含轻量 API）** 与 **方案 2（txecs 中心化中枢）**。

---

## 3. 方案 1：Cloud Run 自包含查询 API + Firestore 暂存 + 飞书通知（轻量闭环）

### 3.1 架构与数据流

```text
[Gmail 收到邮件]
       │
       ▼ (GCP Pub/Sub 推送)
[GCP Cloud Run: gmail-watcher]
       │
       ├── 1. 解析提取: 命中 iam@haier.com，正则提取验证码（如 960616）
       ├── 2. 状态落库: 写入 GCP Firestore (集合 verification_codes/haier)
       │       { code: "960616", phone: "18030768069", received_at: 1732093096, consumed: false }
       └── 3. 人工通知: 调用飞书 Webhook，推送卡片到用户手机：“收到海尔登录验证码: 960616”
       
       ▲
       │ HTTP GET 轮询 (带 Bearer Token，请求参数 since=T0)
[Webdock2 登录程序]
       1. 点击页面“发送验证码”，记录当前本地时间戳 T0
       2. 以 2 秒间隔请求 Cloud Run: GET /api/latest-otp?type=haier
       3. 校验 received_at >= T0 且 consumed == false，获取验证码 960616
       4. 填入网页完成登录，并调 POST /api/consume-otp 标记已消费
```

### 3.2 为什么这么设计？
- **顺应网络流向，杜绝穿透故障**：Webdock2 主动出站向 Cloud Run 公网域名发起请求，不需要搭建反向 SSH 隧道、Cloudflare Tunnel 或配置内网穿透端口映射，网络链路最稳、故障面最小。
- **复用既有技术栈，零新增基建**：`gmail-watcher` 现有代码中已经完整接入了 GCP Firestore（记录 `last_history_id`），并且自身就是 Flask Web 服务，天然拥有公网 HTTPS 域名。无需采购或配置任何新的云服务。
- **天然的解耦与容错**：邮件提取与登录消费各自独立。无论 Cloud Run 容器是否冷启动、登录程序何时发起查询，Firestore 保证数据在 15 分钟内随取随用。

### 3.3 利弊分析
- **优势（Pros）**：
  - **极简自治**：改动完全收敛在 `gmail-watcher` 仓库内部，无需改动外部系统（如 `txecs` 或 `meidi-auto`）。
  - **网络无依赖**：无需内网穿透组件，不依赖 Tailscale 或反向代理保活。
  - **双轨满足**：飞书推送负责“发给人”，HTTP API 负责“发给程序”，互不干扰。
- **劣势与权衡（Cons）**：
  - **冷启动轻微延迟**：若 Cloud Run 长时间闲置缩容为 0，Webdock2 初次轮询可能遇到 1~2 秒冷启动延迟（不过 60 秒轮询窗口完全可以平滑覆盖）。
  - **鉴权开销**：需要在 Cloud Run 上实现基础的 Token 鉴权（配置在 Secret Manager / 环境变量），防止接口被未授权探测。

## 4. 方案 2：基于 txecs 业务中枢中转（Redis 暂存 + 飞书通知集成）

### 4.1 架构与数据流

```text
[Gmail 收到邮件]
       │
       ▼ (GCP Pub/Sub 推送)
[GCP Cloud Run: gmail-watcher]
       │
       ├── 1. 解析提取: 命中 iam@haier.com，提取 960616
       └── 2. 外部投递: POST 推送到中心节点 txecs: https://api.hydwang.xyz/api/v1/otp/ingest
                               │ (带 Service-to-Service Token)
                               ▼
              [txecs 生产中心: backend-api / Redis]
                               ├── 1. 存入 Redis: SETEX otp:haier:18030768069 900 "960616"
                               └── 2. 调度通知中枢: 推送飞书卡片至用户手机
                               ▲
                               │ 内网反代 / 域名查询 (GET /api/v1/otp/latest?type=haier)
              [Webdock2 登录程序]
                               1. 触发登录后，向 txecs 轮询 Redis 中的最新验证码
                               2. 消费后 DEL 或设置标记位
```

### 4.2 为什么这么设计？
- **符合系统整体的“单中心”治理理念**：在当前整个基础设施中，`txecs` 是公网中心边界，负责统一运行 PostgreSQL、Redis、SSO、通知中枢（`business-cn-backend-api-1` / `doc-sync-worker`）。将验证码汇聚到 `txecs`，符合既有架构职责划分。
- **多来源统一聚合能力**：如果未来不仅有海尔邮件验证码，还有美的、供应商短信、其他平台验证码，`txecs` 可以充当全局的“通用验证码中心”。
- **利用 Redis 原生 TTL 机制**：Redis 原生支持 `SETEX` 过期时间（如 900 秒），到期自动物理销毁，省去自建清理机制。

### 4.3 利弊分析
- **优势（Pros）**：
  - **中心化管控与多端复用**：验证码生命周期和通知策略由中心业务网关统筹，未来扩展其他端（如移动端或多台 Webdock 算力节点）更规范。
  - **与现有通知中枢无缝结合**：直接复用现有的飞书消息中枢模块，卡片展示能力更强。
  - **内存级极速读写**：基于 Redis 缓存，轮询性能更平滑。
- **劣势与权衡（Cons）**：
  - **跨系统链路变长**：增加了数据在 Cloud Run -> txecs 之间的网络跳数，系统故障点增加。
  - **侵入范围更广**：除了修改 `gmail-watcher`，还需要修改 `txecs` 上的 `backend-api`（新增路由、鉴权和 Redis 存储模型），开发与部署协同成本较高。

---

## 5. 方案对比与选型建议

| 维度 | 方案 1：Cloud Run 自闭环 + Firestore | 方案 2：txecs 中心化 Redis 中转 |
|---|---|---|
| **改动范围** | 仅改动 `gmail-watcher` 单个仓库 | 涉及 `gmail-watcher` + `txecs` (backend-api) 两个系统 |
| **基础设施依赖** | 现成资源（Cloud Run + Firestore） | 依赖公网域名、Nginx、Redis、内部服务认证 |
| **网络鲁棒性** | 高（Webdock2 直连 Google 服务） | 较平稳，但增加了中间链路 |
| **多业务聚合潜力** | 针对当前 Gmail 来源最为聚焦 | 极高，易于拓展为通用验证码网关 |
| **落地实施周期** | **半天内可完成开发、测试与上线** | 需要跨系统协调与多端部署 |

### 推荐结论
- **当前阶段强烈推荐 方案 1**：对于当前“Gmail 监听海尔验证码并向 Webdock2 传递”的具体需求，方案 1 是投入产出比最高、侵入性最小、鲁棒性最好的解法。
- **演进路线**：后续若出现海尔/美的多渠道、多终端混合验证码（如短信+邮件）的复杂并发场景，可再将方案 1 的写入端无缝重定向至方案 2 的中心网关。
